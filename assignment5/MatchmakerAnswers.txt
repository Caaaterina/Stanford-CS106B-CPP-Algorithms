Q1:
The runtime of fastMaxWeightMatching is O(n^3).

Justification using the timing data (all times in ms from the Time Tests output):
When n doubles, if the runtime is O(n^2) the time should scale by about 2^2 = 4; if it is O(n^3) it should scale by about 2^3 = 8. My measured ratios when n doubles are:
- n = 100 to 200: 13.6884 ms to 72.785 ms, ratio ≈ 5.32
- n = 200 to 400: 72.785 ms to 454.818 ms, ratio ≈ 6.25
- n = 250 to 500: 126.401 ms to 865.888 ms, ratio ≈ 6.85

These ratios are all clearly larger than 4, so the growth is faster than O(n^2). They are also closer to 8 than to 4 (real runs include constant overhead, so we do not expect a perfect 8). Estimating k with k ≈ log(t2/t1) / log(n2/n1) for doubling gives k ≈ 2.4, 2.6, and 2.8 on those intervals, trending toward 3. Therefore the best match is O(n^3).

Q2:
Using the O(n^3) model t(n) ≈ c·n^3 and my measured time at n = 500, t(500) = 865.888 ms, I predict the time at n = 5000 by scaling:
t(5000) ≈ t(500) · (5000/500)^3 = 865.888 ms · 10^3 = 865,888 ms.

Converting units: 865,888 ms = 865.888 s ≈ 14.4 minutes (about 14–15 minutes).

So on my machine, finding a maximum-weight matching for 5,000 people would take on the order of 15 minutes, consistent with both the measured data at n = 500 and the O(n^3) runtime from Q1.

Q3:
I want the largest n with t(n) ≤ 24 hours. Twenty-four hours is 24 × 3600 s = 86,400 s = 86,400,000 ms.

Using t(n) ≈ c·n^3 with c fixed by t(500) = 865.888 ms:
86,400,000 ≥ 865.888 · (n/500)^3
(n/500)^3 ≤ 86,400,000 / 865.888 ≈ 9.98 × 10^4
n/500 ≤ (9.98 × 10^4)^(1/3) ≈ 46.5
n_max ≈ 500 × 46.5 ≈ 23,200.

So I estimate the largest n that still finishes within 24 hours on my computer is about 23,000–23,200 people (rounding down to stay under the limit). This estimate uses the same runtime data and O(n^3) scaling as in Q1 and Q2.
